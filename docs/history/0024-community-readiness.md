## Limitations

- GitHub labels, Security Advisories, `main` protection and the required KASAN status were not
  configured or verified; `docs/labels.md` carries the script, the configuration is a separate
  maintainer action.
- Run times remain unmeasured; the documents cite only the CI timeouts (35 min for the VM,
  150 min for KASAN, 600 s for the QEMU phase).
- `tests/ipc.c` is compiled and copied to the guest but is not called by `vm/suite.sh`; recorded
  in `docs/testing.md` as an observation, without change.
- `vm/*.sh` and `vm/init` have no SPDX line; the CI check covers only C sources, as the plan
  asked. Adding SPDX to the scripts is a starter task (section 4, item 13).
- `site/index.html` did not get the banner (section 9 of the plan provides for it); left for the
  site round. Note of 2026-10-10: done in the "SEO/GEO" section below.
- The commits of this branch from before the DCO adoption have no `Signed-off-by`; the check only
  applies to the PR range and the rule is not retroactive. If the PR includes old commits without
  sign-off, the job will fail and the maintainer decides between a rebase with `-s` or a merge
  after `main`.

## Note of 2026-10-10: intermittent harness failure in the KASAN run of PR 3

Run 38087839385 failed at `fl-remove`: `dmsetup remove fl` returned "Device or resource
busy" right after the `umount` of the `dm-flakey` device, with udev active on the GitHub runner
(message "Udev is running and DM_DISABLE_UDEV ... is set"). No kernel diagnostic; the same
suite passed on `main` and on the phase 3b branch. Probable cause: a race between udev and the
device removal. Fix: `dmsetup remove --retry` for both devices (`lw` and `fl`); run redone by
the pull request trigger.

## Note of 2026-10-10: boot diagnostic of the debug kernel in the KASAN run of PR 3

Run 38089702141: the whole suite passed (`IO_ERROR_INJECTION_PASS` and the other markers), but
the final `dmesg` scan found `BUG: KASAN: wild-memory-access in do_raw_spin_lock`, emitted at
1.7 s of boot by the `swapper/0` process, in an interrupt during `identify_cpu` (stack:
`handle_edge_irq`, `asm_common_interrupt`, `intel_unlock_cpuid_leafs`, `arch_cpu_finalize_init`,
`start_kernel`), before any module of ours. The kernel became "tainted" and turned off lockdep,
so the run also lost coverage. The same 6.12.112 kernel had passed clean in run 38079499011; the
runner runs QEMU without KVM (TCG). Decision: `vm/kasan-guest.sh` checks `dmesg` before loading
the layer and, if there is a diagnostic, prints `MOOBFS_VM_ENV_FAIL` and exits; the workflow
retries once only in that case and never for `MOOBFS_VM_FAIL`. The boot report goes to
`build/vng/dmesg-boot.txt` and to the artifacts. The cause in the debug kernel under emulation
was not investigated; it stays as an observation for the test infrastructure issue.
