# 0203 — Debian 6.12.113 in VM CI; support pending fstests

Date: 2026-10-26. Status: test infrastructure prepared locally; CI and fstests pending.
Work started about 10:20 UTC and ended about 10:30 UTC on 2026-10-26. This is
calendar time, not a measured effort estimate. Issue: [142](https://github.com/studiomoob/llmoobfs/issues/142).

## Goal and decision

Prepare phase 1 of issue 142 under the test-infrastructure allowance in ADR-0022:
make the Debian kernel of `make vm-test` selectable and run both the existing
6.12.111 kernel and 6.12.113 in CI. Keep 6.12.111 as the default and retain the
`Native Linux VM` job name required by branch protection; add a separate job for
6.12.113. Both jobs run on every pull request, including changes to `layer/` or
`vm/`. Each saves its own evidence artifact. The base image digest stays pinned,
as do both kernel image/header package pairs. The two allowed selections are
explicit in the Dockerfile; other values fail the build.

The alternative of adding 6.12.113 immediately to `scripts/supported-kernels`
was deferred. Compatibility rule 3 also requires fstests `quick` on ext4, btrfs
and XFS. There is no result for those runs or for the new CI job yet. The
installation guide in `docs/operations.md` §1 consequently stays as written,
and 6.12.113 remains unsupported.

## Changes and evidence

- `vm/Dockerfile` selects one exact Debian image/header pair:
  `6.12.111+deb13-amd64=6.12.111-1` or
  `6.12.113+deb13-amd64=6.12.113-1`. `vm/run.sh` passes
  `MOOB_DEBIAN_KERNEL` to the build and container; `vm/in-container.sh` uses
  it for headers, modules and the guest kernel.
- `.github/workflows/ci.yml` adds `Native Linux VM (Debian 6.12.113)` with
  `MOOB_DEBIAN_KERNEL=6.12.113 make vm-test`. The existing `Native Linux VM`
  invocation and name stay in place.
- The pinned `debian:trixie-slim` image's `apt-cache policy`, after
  `apt-get update`, reported both `linux-image-6.12.113+deb13-amd64` and
  `linux-headers-6.12.113+deb13-amd64` from trixie-security at
  `6.12.113-1` (source in `docs/references.md`).
- `docker build --platform linux/amd64 --build-arg MOOB_DEBIAN_KERNEL=6.12.111
  -t moobfs-vm-111-issue142 -f vm/Dockerfile .` exited 0. The same command
  with `6.12.113` and tag `moobfs-vm-113-issue142` exited 0. Both temporary
  images were removed after validation.
- `rhysd/actionlint:1.7.7` accepted the CI workflow. The CI lint command
  `shellcheck --shell=sh $(git ls-files 'vm/*.sh' 'scripts/*.sh')` exited 0
  with both `koalaman/shellcheck:v0.9.0` and `:stable`. The two temporary
  ShellCheck images were removed. `sh scripts/check-retired-claims.sh`
  printed `RETIRED_CLAIMS_OK`; `sh scripts/check-pins.sh` printed `PINS_OK`;
  `python3 scripts/check-site.py` reported 12 valid HTML pages. `sh
  scripts/check-spdx.sh` and `git diff --check` exited 0 without output.

An accidental local `make vm-test` invocation occurred while drafting an Orca
question with shell-interpreted backticks. It was interrupted during container
preparation, before any observed QEMU boot, and its container and image were
removed. Its test output is not counted as VM evidence.

## Limits and next step

No complete `make vm-test` or module behavior test on 6.12.113 ran locally:
this task forbids local VM execution while the dedicated host measures latency.
The builds establish package availability and image construction only. The
coordinator will seek approval before pushing so CI can run both kernels. If the
module fails to build or behave on 6.12.113, stop and refer the kernel fix to
the maintainer. After a passing CI run, record one fstests `quick` run per lower
filesystem on the dedicated host, then consider the
`scripts/supported-kernels` change, `docs/operations.md` §1 and
`make install-test` on 6.12.113 without a kernel switch.
